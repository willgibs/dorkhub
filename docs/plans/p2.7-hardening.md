rounds (P2.6, P3-A) were complete and its stop point reached. Board scope

## H5 — second pass (the full 46-finding audit landed)

The audit workflow completed after H3 shipped, with 46 findings surviving
adversarial verification. Most were already covered by H1–H3; these were not:

- **Admin retro window (high — fourth sighting of the class).** The human
  safety net fetched the newest 50 approved+undecided candidates and filtered
  on live stars in JS afterwards. Probed live: exactly 4 of 200 qualify, sitting
  at ranks 43–46 — about **four more auto-publishes** from the section reading
  "none" permanently, with no signal. Now filtered in SQL on the *embedded live*
  `projects.stars_count` before the LIMIT. Filtering the candidate's stale
  snapshot (as `screen.ts` does) would have narrowed the window at the cost of a
  new blind spot for repos that lost stars since ingest; the embedded-column
  filter has neither problem. Probed live before relying on it.
- **Fail-closed caps.** `reportProject`'s 5/24h limit destructured only
  `{ count }`; a failed count yields `null`, `count ?? 0` read that as zero, and
  the limit was skipped precisely when DB pressure made failure likeliest — and
  it is the only control bounding how many *distinct* projects one account can
  report. Same fail-open in `createList` (LIST_CAP) and `toggleListItem`
  (ITEM_CAP).
- **RLS behavioral gaps.** Nothing in either suite exercised the `using` clauses
  of `collections_update_own`, `collections_delete_own`, or
  `collection_items_delete_own` — §3a compares policy name+cmd, never the
  expression — while the list actions delegate authorization *entirely* to them
  (`.eq('id', …)`, no `profile_id` filter). T23/T24 add cross-owner
  rename/visibility/delete and cross-owner item delete. T21's item assertion was
  **vacuous**: it joined through `collections`, so a private list's item vanished
  because its *list* was hidden, whatever `collection_items_select` said. It now
  asserts directly by id. Both were negative-controlled against deliberately
  widened policies (inside the suite's own rolled-back transaction).
- **`ON_ERROR_STOP` in both suites.** Found while running those negative
  controls: psql ran past a raised `RLS FAILURE` and still printed
  "ALL CHECKS PASSED", because that notice sits after `rollback;`. The header
  had claimed a failure aborts the script since M1; now it actually does.
- **Coupling/correctness:** `OPEN_REPORTS_WINDOW` shared between the screen
  engine (was 50) and the admin reports view (100) — reports 51–100 were visible
  to a human but invisible to AI triage; `/api/me/lists` imports `LIST_CAP`;
  both screen selections filter `status = 'published'`; the engagement overlay
  **chunks** at `MAX_IDS_PARAM` (a 400-item list silently dropped every id past
  the 100th, and 400 uuids overran the header budget, losing engagement state
  for the entire page); the pipeline reports `screenHasMore`.

### Deliberately deferred to Fable (with reasons)

Judged architecture or product taste rather than defects, so left rather than
decided unilaterally:

- **A later report can silently clear an earlier `flagged` verdict.**
  `moderation_screens` upsert-overwrites (locked decision D5), so a re-screen
  that comes back `ok` erases a prior `flagged`. Bounded today — AI is
  triage-only, so the loss is queue *ordering*, and the report itself still
  shows — but it is a safety-system property that contradicts nothing less than
  a locked ADR, so it is Fable's call whether `flagged` should be sticky until a
  human resolves it.
- **Admin manual enrich drain sits outside the AI budget** (~120 calls per
  click, unbounded clicks, no daily counter). D3 explicitly left it untouched;
  reconciling it with the cost-discipline principle is a product call.
- **Pass 3 (safety) is starved by passes 1–2 when there is a backlog, and no AI
  call carries a timeout.** Pass ordering is D3 architecture. The missing
  per-call timeout is a genuine robustness gap worth folding into that review.
- **The screen engine walks `decided_at` ASC; the admin retro section walks
  DESC.** The P2.6 ADR claims the two populations "match exactly"; they are
  opposite ends of the same list. H5 aligned *which rows qualify*, not the order.
- **Home recs rail**: a 12-row candidate window filtered by an up-to-100-id
  exclusion set can empty completely — same window-then-filter class, low impact
  (the rail just renders nothing), left so it can be fixed with the others.
- Public list item counts count projects that are no longer visible, so index
  and detail disagree after a moderation unpublish.
- `createList` dead-ends with generic copy after 5 slug collisions;
  `deleteList`'s failure path redirects to `/`; `EditListForm` reports a partial
  multi-action failure as a whole-form failure and has no pending/success state;
  the admin reports section fetches `projects.status` but never renders it, so
  "unpublish" reads as a no-op; `parseScreenResult` can clip a surrogate pair.
- Design/taste: verdict-chip typography, the `//` kicker not `aria-hidden`,
  "N items" hardcoded and pluralized three ways with font drift, lists-index
  `<title>` not naming its owner, the profile list link's unique hover.
